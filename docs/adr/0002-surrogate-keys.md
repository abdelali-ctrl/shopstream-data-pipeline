# ADR-002: Surrogate keys on dimensions and facts

- **Status:** Accepted
- **Date:** 2026-04-28
- **Deciders:** Abdelali Amassaghrou
- **Related:** ADR-001 (raw vs. staging naming)

## Context

In v1, dimensions and facts joined on natural keys exposed by the source PostgreSQL database (`user_id`, `product_id`, `order_id`). At ShopStream's current scale (~500 users, ~200 products, ~2k orders) this is fine. The question is whether to plan ahead.

A natural-key join becomes painful when:

1. **A second source system arrives.** Two CRMs, both with their own integer `user_id` starting at 1, will collide.
2. **A natural key changes type or format.** Migrating `user_id` from `INT` to `UUID` rewrites every fact table.
3. **A natural key is mutable.** Email-as-PK breaks when a customer changes their email.
4. **The fact joins many dimensions.** Multi-column joins on natural keys are hard to optimize and harder to read.

ShopStream is single-source today and may stay that way. But a portfolio project that demonstrates senior data engineering should show the canonical Kimball pattern — and doing it now is cheap, while retrofitting it later means rewriting every fact and every mart.

## Decision

Adopt **MD5-based surrogate keys on every dimension and fact**, generated by `dbt_utils.generate_surrogate_key`.

Each dimension exposes both keys:

| Column | Role |
|---|---|
| `customer_key` | Surrogate, PK, used by all FKs from facts. Stable across source changes. |
| `customer_id` | Natural key from source. Preserved for traceability and for joining back to the source database during debugging. |

Facts FK exclusively to surrogate keys. Marts join exclusively on surrogate keys.

```sql
{{ dbt_utils.generate_surrogate_key(['user_id']) }} as customer_key
```

## Consequences

**Positive**

- Multi-source onboarding becomes a non-event: a new CRM lands its rows with its own natural key, and the surrogate key derived from `(source_system, natural_key)` keeps things unique.
- Type-change resilience: changing `user_id` from `INT` to `UUID` no longer cascades through every fact.
- The signal value: this is the textbook Kimball pattern, and reviewers expect to see it in a senior-grade portfolio project.

**Negative**

- Joins are now on opaque MD5 hashes, which are unreadable in ad-hoc SQL. Mitigation: every dimension preserves the natural key, so debugging joins back to source is a one-line `WHERE customer_id = 42`.
- A small CPU cost on every model build for the MD5 computation. Negligible at this scale.
- One more abstraction layer for newcomers to learn. Standard in the industry; documented here.

## Alternatives considered

- **Keep natural keys forever.** Defensible at a single-source SaaS, but ties the warehouse to one source system's identifier choices.
- **Integer surrogates via row_number / sequence.** Faster to read, but not deterministic across rebuilds — a `dbt run` on the same input could produce different keys, which breaks downstream joins. MD5 is deterministic.
- **UUIDs.** No deterministic property when generated client-side; same problem as integer surrogates.

## Migration

v2 implements this for all four dimension/fact models:

- `dim_customers.customer_key` = `md5(user_id)`
- `dim_products.product_key` = `md5(product_id)`
- `fact_orders.order_line_key` = `md5(order_item_id)`
- `fact_orders.order_key` = `md5(order_id)`

The natural keys remain on every dimension; existing queries that joined on `customer_id` continue to work as long as they're updated to read from the dimension and not directly from staging.
